# Продукт Ayvan: видение и дорожная карта

Документ фиксирует решения и планы по развитию продукта: SaaS/один ресторан, мультитенантность, бронирование, онлайн-заказ и оплата.

---

## 1. SaaS и один ресторан

### 1.1 Текущее состояние

Приложение сейчас **однотенантное**: одна БД, один набор данных (меню, настройки, пользователи), один инстанс API, один фронт. Нет понятия «tenant» / «сайт» / «ресторан».

### 1.2 Целевые сценарии

- **SaaS** — один продукт для многих ресторанов: подписка, общий хостинг, изоляция данных по tenant.
- **Один ресторан** — установка «как сейчас» для одного заведения (self-hosted или один tenant в том же коде).

Оба сценария должны поддерживаться **одним кодом**, без двух отдельных репозиториев.

### 1.3 Режим «один ресторан»

- В коде остаётся мультитенантность (модель Tenant, `tenantId` в данных).
- Режим задаётся конфигом: `SINGLE_TENANT_MODE=true` и/или `SINGLE_TENANT_ID=...`.
- Резолвер tenant в API: в single-tenant режиме подставляется tenant из конфига или единственная запись в БД; в SaaS — tenant из subdomain/header/path.
- Фронт в режиме одного ресторана может не передавать tenant — бэкенд сам подставляет единственный.
- Деплой «для одного ресторана»: тот же билд, в `.env` включён single-tenant, в БД один tenant.

## 2. Мультитенантность (SaaS)

### 2.1 Изменения в БД

| Что | Действие |
|-----|-----------|
| **Tenant** | Новая модель: `id`, `slug`/`subdomain`, `name`, `createdAt`, при необходимости `plan`, `status`. |
| **SiteSettings** | Добавить `tenantId`, связь с Tenant. |
| **User** | Либо `tenantId`, либо связь many-to-many (UserTenant) с ролями. |
| **MenuType, Category, MenuItem** | Добавить `tenantId`, внешний ключ на Tenant. |
| **Language** | Оставить глобальным или добавить `tenantId` при необходимости. |

Миграции: создание Tenant, добавление `tenantId` во все перечисленные таблицы, индексы.

### 2.2 Изменения в API

- **Определение tenant** — middleware/guard: по subdomain, заголовку (`X-Tenant-Id`, `X-Tenant-Slug`) или path извлекается tenant и кладётся в `request.tenant`.
- **Сервисы** — все запросы к «данным сайта» фильтруются по `tenantId`: site-settings, menu-types, categories, menu-items, public-menu, translate, users (при привязке к tenant).
- **Auth** — после логина возвращать tenant(ы); в JWT можно класть `tenantId`; проверять доступ пользователя к текущему tenant.
- **Кэш (public-menu)** — ключи кэша включают tenant, например `menu-types:${tenantId}:${locale}`, и инвалидация по tenant.

### 2.3 Фронт

- Tenant передаётся в API (header или query) из subdomain/URL или из конфига в single-tenant.
- При нескольких tenant — выбор «сайта» после логина или из URL.

## 3. Сценарии реализации продукта

### 3.1 Варианты организации кода

| Вариант | Описание |
|---------|----------|
| **A. Один код, два режима** | Один репозиторий, конфиг переключает single/multi-tenant. Рекомендуется. |
| **B. Два билда** | Один код, при сборке флаг (например `VITE_APP_MODE=saas` / `single`), в single-билде часть кода/роутов не подключается. |
| **C. Два пакета/репо** | Отдельно «SaaS» и «self-hosted» — два кода, двойная поддержка. |
| **D. Open-core** | Один код, часть фич (мультитенантность, биллинг, SSO) включается по лицензии/конфигу. |

### 3.2 Модели тенантности

- **Shared DB, shared schema** — одна БД, везде `tenantId`. Подходит для SaaS и single-tenant (один tenant в БД).
- **Database per tenant** — своя БД на клиента. Жёсткая изоляция, сложнее миграции и пулы.
- **Schema per tenant (PostgreSQL)** — одна БД, отдельная схема на tenant. Для текущего продукта обычно избыточно.

Выбор: **shared DB + tenantId** с опциональным single-tenant режимом.

### 3.3 Дистрибуция

| Сценарий | Описание |
|----------|----------|
| Только облачный SaaS | Все клиенты на вашем хостинге. |
| SaaS + self-hosted «один ресторан» | Облако — мультитенант; у клиента — одна установка, single-tenant. |
| Только self-hosted | Клиенты ставят у себя, один ресторан на установку. |
| White-label | Тот же билд под брендом партнёра (облако или on-prem). |

## 4. Продажа разным ресторанам

### 4.1 SaaS (подписка)

- Один инстанс, много tenant’ов.
- Нужно в продукте: мультитенантность, онбординг (создание ресторана + первый админ), биллинг (тариф, период, оплата), изоляция данных.
- Монетизация: помесячная/годовая подписка за ресторан.

### 4.2 Отдельная установка (self-hosted)

- Каждый ресторан — своя установка (свой сервер/VPS или у клиента).
- В коде: режим одного ресторана, упаковка (Docker, инструкция), при необходимости — проверка лицензии.
- Монетизация: разовая лицензия или подписка за установку.

### 4.3 Гибрид

- Мелкие рестораны — подписка на SaaS.
- Крупные/сети — отдельная установка с лицензией.
- Один код с поддержкой обоих режимов.

## 5. Пробелы в текущей системе

### 5.1 Безопасность и надёжность

| Что | Статус | Зачем |
|-----|--------|--------|
| Rate limiting | Нет | Защита от брутфорса и DDoS. |
| Refresh token / продление сессии | Нет | Меньше разлогинов при истечении JWT. |
| Роли (admin / viewer и т.д.) | Нет | Разделение прав. |
| Смена пароля | Нет | Экран «Изменить пароль» в админке. |
| Восстановление пароля | Нет | «Забыли пароль» (важно для SaaS). |

### 5.2 Эксплуатация и мониторинг

| Что | Статус | Зачем |
|-----|--------|--------|
| Health check | Нет | Эндпоинт для оркестраторов и мониторинга. |
| Структурированное логирование | Нет | Продакшен-логи с уровнями. |
| Валидация env при старте | Нет | Понятная ошибка при отсутствии обязательных переменных. |

### 5.3 Документация и процессы

| Что | Статус | Зачем |
|-----|--------|--------|
| Инструкция по установке | Нет | Деплой для self-hosted и «под ключ». |
| Миграции при деплое | — | Явно описать выполнение `prisma migrate deploy`. |

### 5.4 Фронт и качество

| Что | Статус | Зачем |
|-----|--------|--------|
| Единая обработка ошибок API | Частично | Тосты/сообщения при 401, 403, 500. |
| SEO (meta, title) | Частично | Динамические title/meta для страниц меню. |
| Тесты | Минимум | Покрытие критичных сценариев (логин, меню, при tenant — изоляция). |
| Error boundary (React) | Нет | Заглушка при падении компонента. |

### 5.5 Функциональность продукта

- Мультитенантность — см. раздел 2.
- Онбординг / регистрация ресторана — для SaaS.
- Биллинг — для SaaS (подписка, оплата).
- Изображения блюд — проверить полноту загрузки и отображения по полю `imagePath`.
- Резервное копирование — описать в инструкции (pg_dump и т.п.) для self-hosted.

## 6. Бронирование столиков

### 6.1 Назначение

Гость выбирает дату, время, количество человек (и при желании тип стола), оставляет контакты. Ресторан видит заявку и подтверждает/отклоняет.

### 6.2 Что добавить

**БД:**

- **Reservation** — дата, время, кол-во гостей, имя, телефон, email, статус (pending / confirmed / cancelled / no-show), комментарий, при SaaS — `tenantId`.
- Опционально: **Table** (столы: номер, кол-во мест, зона) и слоты по времени.

**API:**

- Публично: создание брони (с валидацией: не в прошлое, лимит по времени).
- Админ: список броней за период, смена статуса, опционально — свободные слоты по дате.

**Публичный фронт:**

- Страница «Забронировать столик»: форма (дата, время, гости, имя, телефон, email) → отправка → сообщение об успехе.

**Админка:**

- Раздел «Брони»: календарь/список на день или неделю, фильтр по дате, смена статуса.
- Опционально: уведомления о новых бронях (звук, badge, email).

### 6.3 Опционально

- Депозит/предоплата за бронь — см. раздел 8.
- Напоминание гостю (SMS/email).
- Столы и зоны (зал, терраса).
- Экспорт в календарь (Google Calendar и т.п.).

## 7. Онлайн-заказ

### 7.1 Назначение

Гость собирает блюда в корзину, указывает время и способ получения (самовывоз, доставка, в ресторане), контакты. Ресторан видит заказ и готовит/доставляет.

### 7.2 Что добавить

**БД:**

- **Order** — номер, статус (new / confirmed / cooking / ready / delivered / cancelled), тип (pickup / delivery / dine-in), желаемое время, адрес доставки, контакты, комментарий, сумма, при SaaS — `tenantId`.
- **OrderItem** — orderId, menuItemId, количество, цена на момент заказа, опции/примечание.
- Опционально: **DeliveryZone** — минимальная сумма, стоимость доставки, время.

**API:**

- Публично: корзина (сессия или временный ключ), создание заказа, при необходимости — расчёт доставки по адресу.
- Админ: список заказов, фильтр по дате/статусу, смена статуса.

**Публичный фронт:**

- Кнопка «В корзину» у блюда; страница корзины; оформление заказа (способ, время, адрес при доставке, контакты); подтверждение «Заказ принят».

**Админка:**

- Раздел «Заказы»: список/карточки, фильтры, смена статуса (принят → готовится → готов/выдан), печать/экспорт для кухни.

### 7.3 Опционально

- Онлайн-оплата — см. раздел 8.
- Зоны доставки, минимальная сумма, стоимость доставки.
- Уведомления: ресторану о новом заказе, гостю о смене статуса.
- Экран/печать для кухни.

## 8. Оплата

### 8.1 Онлайн-заказ

Оплата для онлайн-заказа **нужна**: без неё заказ остаётся только заявкой.

- Интеграция с платёжным провайдером (Stripe, ЮKassa, Tinkoff и т.п.): приём оплаты картой (и при необходимости SBP/кошелёк).
- Сценарий: оформление заказа → оплата (редирект или виджет) → успех → заказ в статусе «оплачен»/«подтверждён».
- В БД: поле `paymentStatus` (pending / paid / failed / refunded), при необходимости `paymentId` от провайдера.

### 8.2 Бронирование

Оплата для брони **опциональна**:

- **Без предоплаты** — только заявка и подтверждение; оплата при визите. Доп. функционал оплаты не обязателен.
- **Депозит/предоплата** — для снижения no-show: после подтверждения брони — «Оплатить депозит»; при успехе — бронь «оплачена»; при отмене — возврат по правилам ресторана.

### 8.3 Единый платёжный слой

Одна интеграция с платёжным провайдером для всего продукта. Использовать для:

- оплаты заказа (обязательно при полноценном онлайн-заказе);
- депозита за бронь (если ресторан включает эту опцию).

## 9. Приоритеты внедрения

### Для быстрой отдачи одному ресторану (self-hosted)

- Health check, логирование, валидация env при старте.
- README/инструкция по установке и миграциям.
- Смена пароля в админке.
- По желанию: роли, rate limit на логин.

### Для SaaS (много ресторанов)

- Всё из предыдущего пункта.
- Мультитенантность (раздел 2).
- Онбординг (создание ресторана + первый админ).
- Биллинг (подписка, оплата).
- Восстановление пароля.
- Тесты на изоляцию по tenant.

### Общее

- Единая обработка ошибок и тосты на фронте.
- При необходимости: refresh token или «запомнить меня».
- Далее: SEO, тесты по критичным сценариям.

### Новый функционал

- Сначала: бронирование (можно без оплаты).
- Затем: онлайн-заказ с оплатой.
- При необходимости: депозит за бронь через тот же платёжный слой.
